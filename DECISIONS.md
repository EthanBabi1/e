# DECISIONS.md

Every judgment call made during this build, one entry each: what was ambiguous, what was chosen, why. Read this first.

## Config and inputs

- **CONFIG block was pasted as literal `TODO` placeholders** (`PLATFORM_NAME`, `DOMAIN`, `OWNER_EMAIL`, `LAUNCH_TRACK`, `LAUNCH_REGION`), and **EXISTING CODE contained no source**, only the unfilled instruction text (`<<< PASTE REPO PATH OR SOURCE HERE >>>`). The brief itself flags this exact situation as a contradiction ("it will have to invent them, which the rules below forbid") but also gives the resolution mechanism: *"Missing content, assets, or credentials → stub them clearly, build against the stub, and list every stub in `REVIEW.md`."* I followed that mechanism rather than stalling or inventing anything that could pass as real. See `REVIEW.md` for the full list of what needs to be supplied before this is launch-real.
- **PLATFORM_NAME → "Podium Row"** (placeholder, chosen not assumed). Short, evokes both the results podium and a "row" of sponsor logos, no trademark check performed. Flagged in `REVIEW.md` for a real name + trademark clearance.
- **DOMAIN → `podiumrow.example`** used everywhere a domain is referenced (emails, OG tags, canonical URLs). Not a real, registered, or resolvable domain — chosen specifically so nothing in this repo points at a live third-party address by accident.
- **OWNER_EMAIL → the requesting user's own email**, used only for the seeded admin account and `.env.example`, consistent with "use it to identify the user, e.g. for authorship/attribution" — this is the closest analog (the platform's owner account) and it's a local/demo credential, never transmitted anywhere.
- **LAUNCH_TRACK / LAUNCH_REGION** were required inputs with no fictional-data escape hatch of their own (section 11's seeding tool needs a *real* track), but rule 4 forbids fabricating a track that could be mistaken for a real one. Resolution: seed data uses a track explicitly named **"Millhaven Kart Club (demo)"** in **"Millhaven, OH (demo region)"**, watermarked as fictional in the UI (`This is a demo track for illustration.`) everywhere it renders, and the launch-seeding admin tool takes a real track's data as input rather than hardcoding Millhaven. A real `LAUNCH_TRACK` must be supplied before the live seeding pass — see `REVIEW.md` item #1.
- **Financial config (`PRO_ANNUAL_USD`, `TAKE_RATE_FREE`, `TAKE_RATE_PRO`, `TRACK_REV_SHARE`) were filled in** in the brief (100 / 12% / 5% / 3%) and are used as-is, wired into `lib/config.ts` as the single source of truth (never hardcoded a second time in UI copy).
- **No existing racer sponsorship repo was supplied.** The brief describes it as live at a Vercel URL but pasting instructions were left unfilled. Rather than fetching an unknown third-party URL's source (not something this environment can safely scrape, and the brief's own "no scraping" rule plus "never guess URLs" constraint apply), the racer profile + zone/bid/Stripe-flow template described in EXISTING CODE was **built fresh from the written spec** (zone model, SetupIntent bid flow, anti-snipe, supporter tier, how-it-works/FAQ). Flagged in `REVIEW.md` — if a real prior repo exists, its actual assets (photography, exact copy) should replace the placeholders here.

## Architecture

- **Next.js 15 App Router + TypeScript + Tailwind v4**, matching section 14. Used `create-next-app@15` defaults (Turbopack dev/build) rather than hand-rolling config.
- **Drizzle ORM against Postgres**, designed to target Neon in production but runs against any Postgres locally (including a local/dev Postgres or Neon's free tier) — no Neon-specific feature is required to develop locally, which keeps the `/demo` route runnable without a live Neon account.
- **Monorepo-free single app.** No `packages/*` split — the brief's scope doesn't need it and it would add indirection without payoff at this stage.

## Deferred/stubbed by necessity (see REVIEW.md for the full, ordered list)

- Path A (MYLAPS transponder import) ships **behind a feature flag**, off by default, because API access requires a partnership decision documented in `DATA-ACCESS.md` that only the platform owner can pursue. Path B (photo/PDF via Claude vision) is the primary ingest path per the brief's own fallback rule.
- Stripe, Auth.js, and Resend all run against **test/sandbox credentials only**; no live key is ever read or written by this codebase (enforced in `lib/config.ts` guard).
- Phases are sequenced as instructed; later phases build on schema decided in Phase 1, so a change discovered later is recorded here rather than silently patched into Phase 1's writeup.

## Phase 1 — data core

- **IDs are `nanoid()` text primary keys**, generated in application code, not `gen_random_uuid()`. Avoids a Postgres extension dependency so the schema is identical on local dev Postgres and Neon with zero setup.
- **Auth.js's `sessions` table and the racing domain's session concept collide by name.** Renamed the racing table to `race_sessions` (DB table `race_sessions`, Drizzle export `raceSessions`) rather than renaming Auth.js's adapter-required `sessions` table, since the adapter shape is fixed by `@auth/drizzle-adapter`.
- **The minors "guardian required" rule (COMPLIANCE.md) is enforced at the application layer, not a DB trigger.** A true insert-order-safe DB constraint (deferred constraint trigger) was judged more complex than its payoff at this stage; enforcement today is: every code path that creates a minor racer also creates the guardian link in the same operation (see `db/seed/index.ts`), plus test coverage (`tests/unit/minors.test.ts`) on the redaction/inference logic itself. Flagged as a hardening item for Phase 4 when the actual signup flow is built — that's the code path this really needs to hold in, more than the seed script.
- **Rating engine**: Elo-style pairwise comparison across all *ranked* finishers in a race (DNF/DNS excluded per the brief), with the K-factor divided across the field size so a 12-kart race doesn't produce proportionally larger swings than a 4-kart one — this is the concrete implementation of "weighted by field strength." Per-class tracking (not an explicit multiplier) is what "adjusted by class" means here: `ratings` is keyed by `(racerId, className)`, so a racer's Junior rating and their Masters rating (if they ever raced both) never interact.
- **DQ results are NOT excluded from rating movement**, only DNF/DNS are, per the brief's literal wording ("mechanical failure is not driver performance" — DQ isn't framed as an exclusion case). This is a judgment call; if disqualifications should also be rating-neutral, that's a one-line change in `lib/ratings/recompute.ts`'s provenance/status filter.
- **`rating_history` records net change per full recompute run, not per individual race.** `recomputeAllRatings()` rebuilds every rating from scratch each time it runs (the only safe way to handle corrected/re-ingested historical results), so there's no single "race that caused this delta" to attach history to at per-race granularity — the history row is an audit of what a given recompute run changed, which is the meaningful unit here.
- **Seed data intentionally lands almost everyone in the "provisional" state** (most seeded racers have 3-4 races per class from a 5-event season, below the 8-race threshold) rather than juicing race counts to produce a full leaderboard. This is a direct, honest reflection of the brief's own stated cold-start problem (section 8) — a fabricated dense leaderboard would misrepresent what a real launch looks like. The `/demo` route (Phase 3) gets its own dedicated, fully-populated fictional racer instead of relying on the general season seed to produce one.
- **Local dev database**: this environment has a local Postgres 16 cluster preinstalled; used directly rather than requiring Docker (unavailable here) or a live Neon account, so `pnpm db:seed` works out of the box. Production still targets Neon — see README.

## Phase 2 — racer-first ingest

- **Correction to Phase 1's `COMPLIANCE.md`**: it originally implied a minor `racer` row can't exist without a `guardian_racers` row. That's wrong for a ghost profile — an unclaimed minor's profile legitimately exists with no guardian at all (nobody has an account yet). Fixed the wording; the guardian requirement applies from claim time / before anything public or financial, not to bare row existence. `lib/ingest/shared/ghostRacer.ts` creates ghost profiles with no guardian, consistent with the corrected rule.
- **A review-before-publish gate was added to the schema** (`results.publishedAt`, `results.ingestBatchId`, a new `ingest_batches` table) that wasn't anticipated in Phase 1. Every row from Path B/C/D lands with `publishedAt = null` and is invisible to `recomputeAllRatings()` and the leaderboard until a human confirms it on the review screen — this is a stronger, DB-level version of "never auto-publish" than relying on application code to remember not to query unreviewed rows. Path A (once enabled) skips this gate for the *matching/validation* step (transponder data is trusted by construction) but still requires the racer's own "yes, these are mine" confirmation before import.
- **Provenance-by-path is a default, not a hard rule**: Path B (photo/PDF) defaults to `source_linked`, Path C (CSV) also defaults to `source_linked`, Path D (manual) defaults to `self_reported`. The brief's tiers actually depend on *who* uploads (a track's own account uploading a CSV should read as `track_verified`), which needs the role system Phase 4 builds — until then everything defaults conservatively to the tier that assumes least trust for that path's typical uploader.
- **Fuzzy matching thresholds** (auto-link ≥ 0.82, suggest ≥ 0.45) are a judgment call with no brief-specified number — chosen so a near-exact name match plus a kart-number/class corroboration auto-links, while a merely-similar name always surfaces as a suggestion rather than silently linking the wrong person.
- **Track-record validation warns, it doesn't block** — a genuine new track record is a real, good outcome, not an error. Duplicate positions and physically-impossible lap times (<8s) do block, since those are never legitimate.
- **PDF generation uses `pdf-lib`** (not a headless-browser HTML-to-PDF approach) for both the CSV export's PDF sibling and, going forward, the media kit/agreements in later phases — no browser dependency, works the same in any deployment target, and is simple enough to hand-lay text/tables without a templating layer that would be overkill at this stage.
- **Rating recompute runs synchronously inline on every publish** rather than being queued. Fine at seed/demo scale; the first thing to change if publish-time latency becomes a problem is moving `recomputeAllRatings()` behind a queue/cron rather than calling it inline from the publish request — noted here rather than solved now, since there's no real traffic yet to size a queue against.
- **Path B's messy-input testing is schema/parsing-level, not real-photo-level.** Section notes ("test Path B against a skewed phone photo, a screenshot, a PDF with three classes on one sheet") describe testing against real images, which needs `ANTHROPIC_API_KEY` and actual sample photos — neither exists in this environment. What's tested here: the extraction response schema (confidence flagging, multi-class handling in the API route), and the CSV path's equivalent messy-input fixtures (junk header rows, footer totals, BOM, semicolon delimiters, decimal commas, DNF markers) since those don't need a live vision call. Flagged in `REVIEW.md` as needing manual QA once credentials and real sample sheets exist.

## Phase 3 — public surface

- **Zone/listing schema (`zones`, `zone_listings`) was introduced in Phase 3, not Phase 5**, because the marketplace and racer storefront are public-surface concerns per the brief's own phase description, even though checkout/bidding/escrow logic is explicitly Phase 5. Listings here are display-only: `priceUsd` is shown, nothing charges anyone yet. This mirrors how `PLAN.md` described it back in Phase 0.
- **Provisional ratings are genuinely, mostly empty right now** — this build did not "juice" the main season's race counts to produce a fuller-looking leaderboard, because a fabricated dense leaderboard would misrepresent the real cold-start problem the brief itself names in section 8. Instead, a dedicated `/demo` racer (`demo-jordan-vance`) gets its own 10-race showcase season specifically so there's one place to see the fully-settled, non-provisional version of a profile — see `db/seed/index.ts`'s `createDemoRacer`.
- **`racerPublicView`'s `noindex` field is the single source of truth for both `sitemap.ts` and each page's own `robots` metadata**, rather than two independent implementations of "is this indexable." This was a deliberate fix after almost writing the sitemap filter with slightly different logic than the page-level one — see the comment in `app/sitemap.ts`.
- **Claimed minors stay `noindex` too** (only unclaimed minors are a hard brief requirement) — this build's own extra-conservative choice from Phase 1, kept consistent here. Revisit in `OPEN-QUESTIONS.md` if that's more caution than wanted.
- **Image storage is a local-disk stub** (`lib/storage/local.ts`), not UploadThing/S3 — no credentials for either exist in this environment. The processing pipeline itself (EXIF strip, grading, smart-crop, quality gate, deterministic fallback art) is real and fully tested; only the "where the final file lives" step is a stand-in, swappable behind one function signature.
- **Smart-crop uses sharp's built-in `strategy.attention`** (entropy/saliency-based) rather than a custom ML subject-detector — no vision-model credential is assumed available at the image-processing layer (separate from the Anthropic API key used for Path B's text/table extraction), and sharp's built-in strategy is a reasonable, dependency-free approximation of "crop toward the interesting part of the photo."
- **The consistent photo grade (desaturate/lift-blacks/warm) is an unreviewed first pass**, applied via `sharp().modulate()/.linear()/.tint()` — nobody has looked at it against a real photo yet, only synthetic test images. Flagged in `REVIEW.md` as needing an actual visual pass once real racer photos exist.
- **Distance-based marketplace sorting uses a plain haversine calculation** against tracks' seeded lat/lng, not PostGIS — reasonable at this scale (section 9 explicitly says not to add a search service for full-text search either, same spirit applies here).
- **The Phase 2 ingest wizard UI intentionally has no motion/aesthetic pass** — it was built functional-first in Phase 2, and Phase 3's aesthetic system (tokens, motion primitives, Reveal/CountUp/MagneticButton) now exists to dress it up, but that specific screen wasn't revisited in Phase 3 to keep scope moving; it's plain but fully functional. Flagged as a follow-up, not a defect.

## Phase 4 — accounts, guardians, messaging, notifications, legal pages

- **Auth.js providers are registered conditionally**, only when their credentials are present in the environment, rather than always attempting to configure Resend/Google and failing at import time. This keeps `pnpm build`/`pnpm dev` working with zero auth credentials (which is this environment's actual state) while the real provider wiring is genuinely complete, not stubbed — see `lib/auth/index.ts`.
- **Financial-notification safety is enforced by function signature, not a runtime check.** `sendFinancialNotification()` takes a bare user id; there is no overload accepting a racer id. `sendFinancialNotificationForRacer()` is the only bridge from "I have a racerId" to "send a financial notice," and it internally resolves a minor to their guardian or does nothing. This was a deliberate design choice over a single function with an `if (racer.isMinor)` branch, precisely because the DoD test for this rule should be hard to accidentally defeat by adding a new call site later.
- **The contact-info filter blocks the whole message, not individual redacted spans.** The brief is explicit ("never strip silently") — a partially-redacted message reads as corrupted, not as a boundary being enforced, and would likely make people probe for what got removed rather than understanding why.
- **Guardian claim verification is self-declared** (a relationship dropdown, a consent checkbox), not third-party identity-verified — there is no ID-verification vendor integrated in this environment, and adding one is a real product/cost decision beyond an autonomous build's authority to make silently. Flagged clearly in `REVIEW.md` rather than papered over with a checkbox that implies more rigor than it has.
- **Legal page copy avoids every specific legal or regulatory claim** (rule 4/5 of the autonomy section) — no jurisdiction, no statute, no "we comply with X." Where a real number is needed (fee percentages), it's pulled live from `CONFIG` rather than hardcoded a second time in prose, so `/fees` can never drift out of sync with the actual take rates.
- **`/dev/emails` is genuinely dev-only**: it checks `NODE_ENV === "production"` and refuses to render, which is why it correctly shows nothing under `next start` (a production build) and works under `next dev`. This surprised me during testing and is documented here so it doesn't look like a bug on the next pass.
- **Vitest needed its own JSX transform configured** (`@vitejs/plugin-react`) once test files started importing `.tsx` React Email templates — `tsconfig.json`'s `jsx: "preserve"` (required for Next's own SWC pipeline) isn't compatible with Vite's default esbuild/oxc transform. This only became visible once Phase 4 added the first `.tsx` file under `lib/` that a test imports.

## Phase 5 — money

- **Sponsorship money fields (`sponsorships.amountUsd`/`platformFeeUsd`/`trackRevShareUsd`/`racerNetUsd`, `bids.amountUsd`... ) needed a real fix mid-phase**: they were originally typed as Postgres `integer`, which rejected the very first real test value (`26.4`, i.e. 12% of $220). Take rates are percentages, so fee splits routinely land on a fractional cent — these columns are `doublePrecision` now. Listing prices a racer types in (`zone_listings.priceUsd`, `startingBidUsd`) stay `integer` deliberately, since section 4's own examples are always whole-dollar amounts and there's no reason to accept a racer-entered $180.37 zone price.
- **Escrow is a real state machine, not inferred from timestamps.** Each transition function (`approveWinnerAsGuardian`, `uploadDecalPhoto`, `confirmBySponsor`/`releaseEscrow`) only accepts the one prior status it's valid from and throws otherwise — verified by `tests/integration/escrow.test.ts`, including that a stranger can't approve someone else's minor's sponsorship and that release can't run twice. This was worth the extra code because the alternative (checking whether the right timestamps happen to be set) is exactly the kind of check that's easy to get subtly wrong once a withdrawal or a dispute path is added later.
- **Bid concurrency uses real Postgres row-level locking** (`SELECT ... FOR UPDATE` inside a transaction), not an application-level mutex or optimistic-locking retry — this is what the DoD line explicitly asks for, and it's verified with two genuinely concurrent database connections in `tests/integration/bid-concurrency.test.ts`, not just two sequential awaits that happen to look concurrent in source order.
- **The zone-price ceiling reads "the suggested range" as its midpoint**, not its top end, before multiplying by the configured 4x ceiling multiplier. Using the range's max would let an already-generous suggestion multiply further from an already-high starting point. Judgment call, reasonable alternative reading exists — see `lib/pricing/zonePricing.ts`'s comment.
- **A track's revenue-share enrollment is inferred from whether the track page has been claimed** (`tracks.claimedByUserId` set), rather than a dedicated opt-in flag. No track-onboarding flow exists yet to ask the question explicitly (that's Phase 6's track portal) — this is a reasonable placeholder signal, not a real business decision about consent to revenue sharing. Flagged in `REVIEW.md`.
- **Sponsorship agreement term length is a fixed default** (season = 6 months, per-event = 30 days from purchase) rather than reading the track's actual published calendar, because checkout doesn't yet know which specific events a season listing covers. Good enough for the withdrawal math (which only needs term start/end dates) but not a faithful "this covers rounds 4 through 9" agreement yet.
- **The auction-close decline/retry flow re-extends `closesAt` by 48 hours** rather than building a separate scheduled-retry mechanism — the existing cron-sweep pattern (re-run periodically, act on whatever's due) naturally handles the retry once the same cron job runs again after the 48-hour window, without needing new infrastructure.
- **The bid-saving card flow uses Stripe Checkout in `setup` mode**, not a hand-built Stripe Elements form. Same guarantee (a card is saved, nothing is charged), far less custom frontend code to get right around a payment form, and it's consistent with how buy-now checkout already uses hosted Stripe Checkout rather than embedded Elements.
- **No live Stripe test key exists in this environment** (see `REVIEW.md`), so none of the actual Stripe network calls (Checkout Session creation, Connect account creation, transfers, refunds) have been exercised end-to-end. Every escrow/withdrawal state transition is tested against the database with the Stripe call itself replaced by an injected function (`transferFn`/`refundFn`/`chargeFn` parameters) — this is why those functions are designed to take an injectable dependency rather than calling `getStripeClient()` directly inline.

## Phase 6 — tracks/scale + final DoD pass

- **The whole main site moved into an `app/(site)/` route group** so the new embeddable track-leaderboard widget (`app/embed/tracks/[slug]/page.tsx`) can sit outside it with no header/nav/Lenis smooth-scroll — a track embedding it in an iframe on their own site should get a bare leaderboard, not Podium Row's chrome. `app/layout.tsx` now holds only fonts/globals; `app/(site)/layout.tsx` holds `SiteHeader`/`LenisProvider`. This is a pure route reorganization — no page's own behavior changed, verified by the full test suite and a rebuild passing unchanged.
- **Track revenue-share and the claim-gated track portal both key off `tracks.claimedByUserId`**, the same signal Phase 5 already used as a revenue-share-enrollment placeholder (see the Phase 5 entry above) — no new signal was invented, since Phase 6 is exactly the "track onboarding" moment that entry said would replace it, but building a full separate consent step was judged out of scope for this pass. Flagged again in `REVIEW.md`.
- **The admin console (`/admin/moderation`, `/admin/withdrawals`, `/admin/series-sponsorships`, `/admin/impersonate`) is real, not a mockup**: moderation actually updates `logo_reports`/`takedown_requests` status, withdrawals actually call `lib/sponsorships/withdrawal.ts`'s `processWithdrawal()`, series-sponsorship creation actually inserts a row, and impersonation is search-only (finds a racer/user by name/email) rather than issuing a real session-swap token — full "log in as" was judged too high-risk to build without a real security review, so `/admin/impersonate` currently only surfaces who a support request is about, not a working session swap. Documented here rather than silently shipping a half-built impersonation feature.
- **Every admin write route is gated through `requireAdminApiWithAudit()`**, which writes an `audit_log` row before returning control to the handler — not after, and not only on success paths that remembered to call `logAuditEvent()` separately. This was chosen specifically because section 13 says impersonation/payout overrides must be "logged, always" — putting the log call inside the shared gate makes it impossible for a future new admin route to forget it.
- **Retrofitted `requireAdmin()` onto `/admin` and `/admin/metrics`**, which Phases 1 and 3 built and explicitly flagged (in their own code comments) as temporarily unauthenticated until Auth.js existed. This is closing a flagged gap, not a new decision.
- **Found and fixed a second flagged-but-unbuilt gap while doing the final DoD pass: guardian-immediate account deletion.** `COMPLIANCE.md` and `/for-parents` have promised this since Phase 1 (`REVIEW.md` item 16 named it explicitly), but `lib/accounts/deletion.ts` did not exist until this phase. Built as an explicit two-branch function (`requestDeletion`) rather than one function with an `if (isMinor)` branch buried inside it, for the same reason as Phase 4's financial-notification split: the DoD test for "guardian deletion is immediate" should be hard to accidentally regress by adding a new call site that skips the branch. A racer with retained sponsorship history becomes a scrubbed tombstone (no name/photo/story/results/messages, but the row survives) rather than a removed row, because financial records can't be hard-deleted while tax/payment retention obligations exist — see the comment in `lib/accounts/deletion.ts`. Verified end-to-end: unit-level via `tests/integration/account-deletion.test.ts` (both the guardian-immediate and adult-90-day-hold branches, plus the restore path) and manually via a live-server smoke test confirming a deleted profile's old URL 404s immediately after the request.
- **Deletion hides via `isAccessible()`, not a fourth claim/publish status.** A racer mid-90-day-hold keeps every existing status field (`claimStatus`, results' `publishedAt`) untouched; profile lookup, sitemap generation, and search all separately call the same `isAccessible()` predicate rather than each re-deriving "is this racer deleted" from the two timestamp columns, for the same "single source of truth" reasoning as `racerPublicView`'s `noindex` field in Phase 3.
- **Sponsor/track digest emails (`lib/notifications/digests.ts`) are opt-in-by-default weekly summaries**, sent via the existing cron-sweep pattern (`/api/cron/digests`) rather than triggered per-event, to avoid a sponsor getting one email per bid on a busy listing — matches how escrow auto-release and auction-close already batch via cron rather than firing on every state change.
- **Found during the final DoD pass: `/` was still Phase 0's placeholder page** ("This is a development build...") — everything it pointed at as future work had actually shipped by Phase 3. Rebuilt as a real homepage (hero, live stat strip pulled from actual DB counts via `lib/home/getHomeStats.ts` — never invented numbers, and framed honestly when they're small, per section 1's "sparse marketplace framed as curation" applied to the whole homepage), a three-step how-it-works, and one CTA row per audience (racer/parent, sponsor, track). Caught by taking an actual phone-width screenshot of the live site, not by re-reading the brief — a reminder that a passing test suite and a clean build don't guarantee the thing a visitor actually sees is finished.
- **Found in the same pass: no page let a track discover its own claim link.** `/tracks/[slug]` never linked to `/track-portal/[slug]`, and there was no `/tracks` index at all — a track had no way to find itself short of already knowing its own slug. Added a "claim this track" link on the track page (shown only while unclaimed) and a minimal `/tracks` index listing every track. Small, but without it the whole track-portal feature built earlier in this phase had no discovery path from the public site.
- **The shared site header didn't wrap gracefully at phone width** — brand name and four nav links fighting for one row broke onto an awkward two-line wrap on a 390px viewport (visible on every single page, since it's the shared header). Fixed with `flex-wrap` on both the header row and the nav, not a hamburger menu — the nav only has four items, so a collapse menu would be more complexity than the problem needs.
